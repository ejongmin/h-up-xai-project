## DART Open API 키 발급

먼저 API 키를 발급받았습니다. 팀원과 각각 받았는데, 계정당 일일 호출 한도가 2만 건이기 때문입니다. 상장사 약 2,500개 × 11개 연도 × 2개 엔드포인트면 단순 계산으로도 5만 건이 넘습니다. 한도를 넘기면 그날은 더 못 받습니다.

키는 코드에 넣지 않고 `.env` 파일로 분리했습니다. 최종적으로 저장소를 공개할 계획이라 이건 처음부터 지키기로 했습니다.

## 수집 파이프라인의 본체는 캐시입니다

코드를 짜면서 가장 신경 쓴 부분은 API 호출이 아니라 **캐시**였습니다.

같은 요청이 두 번 나가지 않게 하고, 결과가 없는 응답까지 캐시합니다. 그리고 한도를 넘기면 조용히 빈 값을 돌려주는 대신 **즉시 멈추게** 만들었습니다. 조용히 넘어가면 며칠 뒤에 구멍 난 데이터셋을 발견하게 되고, 어디가 비었는지 찾는 데 더 오래 걸립니다.

```
한도 초과 → QuotaExceeded 로 중단 → 다음 날 같은 명령 재실행 → 캐시 이후부터 이어서 수집
```

## 변수를 27개로 제한한 이유

재무비율은 마음만 먹으면 수백 개도 만들 수 있습니다. 자동으로 조합해서 파생변수를 뽑으면 성능도 대체로 조금은 올라갑니다.

그런데 이 프로젝트에서는 그렇게 하면 안 됩니다. 최종 산출물이 **실무자에게 보여줄 설명 카드**이기 때문입니다. "변수 137번의 기여도가 높습니다"는 설명이 아닙니다. 변수 하나하나가 재무적으로 해석 가능해야 합니다.

그래서 30개 안쪽을 상한으로 두고 27개로 정리했습니다.

| 범주 | 변수 |
|---|---|
| 수익성 | 영업이익률, 순이익률, ROA, 총자산영업이익률 |
| 안정성 | 부채비율, 자기자본비율, 유동비율, 이자보상배율 |
| 활동성 | 총자산회전율, 매출채권회전율, 재고자산회전율 |
| 현금흐름 | 영업현금흐름/매출, 영업현금흐름/부채, 이익의현금전환 |
| 특수 항목 | 자본잠식, 완전자본잠식, 자본잠식률, 영업손실, 2년연속영업손실 |
| 변화량 | 주요 6개 비율의 전년 대비 변화폭 |
| 성장·통제 | 매출증가율, 자산증가율, 로그자산 |

**변화량을 따로 넣은 이유**가 있습니다. 부채비율이 300%인 기업과, 100%였다가 300%가 된 기업은 전혀 다른 상태입니다. 수준값만 보면 이 둘이 같아 보입니다.

**특수 항목도 따로 넣었습니다.** 자본잠식이나 2년 연속 영업손실은 비율이 아니라 사실상 신호입니다. 실제로 관리종목 지정 사유에도 들어가는 항목들입니다.

## 사소해 보이지만 정한 것 하나

비율을 계산할 때 분모가 0이면 결과를 **0이 아니라 결측으로** 둡니다.

이자비용이 0인 기업의 이자보상배율은 0이 아닙니다. 정의되지 않는 것입니다. 이걸 0으로 채우면 "이자를 전혀 못 갚는 최악의 기업"으로 모델이 학습합니다. 실제로는 무차입 경영일 수도 있는데 말입니다.

## 이번 주에 확인해야 할 것

DART 응답에서 계정 항목을 꺼낼 때 `account_id`(IFRS 표준 코드)를 우선 쓰고, 없으면 계정명으로 폴백하도록 짰습니다. 그런데 기업마다 계정 표기가 일관되지 않을 수 있어서, **표본 20개 기업으로 매핑 성공률을 먼저 재봐야** 합니다.

〔매핑 성공률: 〕
〔실패한 계정과 원인: 〕
