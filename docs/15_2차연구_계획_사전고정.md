   감사의견 사건일도 정정본 날짜로 잡혀 자기 연도 의견이 라벨이 됐다(131행, 10-13 수정).

> 발표용 문장 — "1차 분석에서 정정 공시와 평가 구간 재사용이 결과의 신뢰성에 영향을 줄 수 있음을 확인했습니다.
> 이를 바탕으로 최초 공시 원문에 근거한 데이터와 사전에 고정한 평가 절차로 후속 검증을 진행하고자 합니다."

목표는 '다시 돌려서 좋은 수치'가 아니라 **오류가 생긴 경로를 찾아, 재발하면 감지되는 절차**다.
오류가 없다고 보장할 수는 없지만, 발견하고 추적할 수 있는 구조로 만든다.

## 1. 연구 질문 〔확정 필요〕

- **주 목적**: 관측 기간 내 첫 부실 예측 — T 시점까지 관측된 부실 이력이 없는 기업이 T 이후 400일 안에 처음 부실해지는가.
- 보조: 전체(반복 포함), 반복 부실. 반복 부실은 과거 이력만으로도 상당 부분 맞혀지므로(1차 검증 PR-AUC 0.214) 주 목적에서 뺀다.
- 관측 한계: 사건 원천이 2015-01 부터라 그 이전 이력은 모른다.

## 3. 데이터 재구축 — 최초 공시 원문

- 원천: DART `fnlttXbrl` — **최초 접수번호(rcept_no)의 원본 XBRL** (`src/hup/xbrl.py`). 최초 접수번호는 공시 목록에서 기업·사업연도별 가장 이른 사업보고서 (`dart.first_filings`).
- 값: 당기 = 종료연도가 사업연도인 맥락, 전기 = 그 전년. 기간 값은 1년(350~380일)짜리만. 연결/별도 축 외의 차원(자본 구성요소 등)이 붙은 값은 버린다.
- **기준시점 T = 목록상 최초 접수일과 그 접수번호의 날짜 중 늦은 날.** 2026-10-31 전체 수집에서 접수번호 날짜가 더 늦은 행 3건
  (자정 넘김 1건, 2025-08 재제출로 보이는 2건)을 검사 관문이 '재무 공개일 > T' 로 잡았다. 그 값은 접수번호 날짜에야 공개됐으므로 T 를 늦춘다.
- 기준: 연결 → 별도 → 축 없음 순 (1차와 같은 원칙). 어느 기준인지 `재무제표기준`에 남긴다.
- **원본이 없는 행**(status 013/014)은 패널에서 빼고 건수를 검사 보고서에 남긴다. 주 분석에 넣지 않는다. 〔확정 필요: 별도 분석 여부〕
- 계정명 폴백(1차의 `account_nm`)은 XBRL 에 없다. 계정 코드로만 뽑으므로 결측이 늘 수 있다 — 변수별 결측률을 1차와 대조해 보고한다.
- 1차 단위 보정(`fix_units`)은 그대로 적용하되, 아래 검사 관문이 별도로 의심 행을 표시한다.

**시험 수집 (2026-10-31, 사업연도별 4건 × 11년 = 44건)**
- 44건 모두 원본 XBRL 있음. 최초 접수일이 1차 데이터셋의 T 와 23,084행 전부 일치.
- 1차 API 값과 계정별 일치: 정정본이 아닌 행은 대부분 완전 일치. 불일치는 1차에서 `정정본재무=1`인 행에 몰렸다
  (예: 한 FY2021 행은 12개 계정 중 1개만 일치) — 바로 1차에서 T 이후 정보가 섞였던 행이다.
- 전체 수집: `scripts/collect_xbrl.py` (키 2개로 나눠, 캐시 `data/cache/xbrl/`).

## 4. 데이터 검사 관문 (`src/hup/checks.py`)

통과해야 저장·학습된다. 두 등급.

| 등급 | 검사 | 처리 |
|---|---|---|
| 중단 | 재무 공개일 > 기준시점 T | 하나라도 있으면 build 중단 |
| 중단 | 라벨 1 인데 (T, T+400일] 안에 사건 없음 | 〃 |
| 중단 | 사건 중복 (기업·날짜·유형), 기업-연도 중복 | 〃 |
| 검토 | 자산 10억 원 미만 (단위 의심) | `검토필요=1` → 학습·평가 제외, `results/v2/data_check/검토대상.csv` |
| 검토 | 자산이 수백 배 변동했는데 같은 보고서의 전기값이 확인하지 않음 | 〃 |
| 검토 | 이번 보고서의 전기값 ÷ 전년 보고서의 당기값 ≈ 10³·10⁶ | 〃 |
| 처리 | 연결↔별도 기준이 전년과 바뀜 | 변화량 변수 결측 (기준이 다른 두 값의 차이라서) |
| 처리 | 원본 XBRL 없음 | 패널 제외, 건수 보고 |

검토 대상은 조용히 고치지 않는다. 사람이 `data/manual/검토판정_v2.csv`(corp_code, bsns_year, 판정)에 `유지`라고 적은 행만 다시 들어간다.
회계기간은 파서가 1년 기간만 받는 것으로 막는다.

## 5. 모델 — 기준 모델부터, 같은 조건에서 비교

### 5-1. 1차의 주 모델 선택 근거 (기록, 2026-10-31)

1차에서 히스토그램 기반 그래디언트 부스팅(HistGradientBoosting)을 주 모델로 쓴 이유:
1. **재무변수 사이의 복합적 관계** — 같은 적자라도 부채 부담과 현금흐름에 따라 위험이 달라질 수 있다. 의사결정나무 기반 모델은
   조건의 조합과 비선형 관계를 표현할 수 있고, 기본 로지스틱 회귀는 변수를 따로 구성하지 않으면 이를 표현하기 어렵다.
2. **구현과 실험 관리** — 코드에 적힌 근거는 결측을 직접 처리하고 scikit-learn 만으로 추가 라이브러리 없이 쓸 수 있다는 것(`src/hup/model.py`의 `ensemble`).
   다만 파이프라인에 별도 결측 처리가 있으므로, 결측 처리 능력이 성능을 높였다고 주장할 수는 없다.
3. **예측과 설명 검증을 함께** — 주 모델의 예측을 SHAP 으로 분석하고 로지스틱 계수 방향과 비교하는 구조를 만들었다.
   SHAP 은 다른 모델에도 적용되므로 이것이 이 모델의 우수성 근거는 아니다.

비교가 부족한 점:
- XGBoost · LightGBM · CatBoost · 랜덤포레스트 비교 기록은 없다.
- TabPFN 은 비교 코드가 있으나 라이선스 수락 대기로 실행되지 않았다 (결과 파일이 없다 — 1차에 우리 모델 행만 담긴 빈 결과 파일이 있었으나 10-31 정리).
- isotonic 은 별도 예측 모델이 아니라 출력 확률 보정 단계다.
- 모델 간 성능 차이의 통계적 유의성은 검정하지 않았다.

따라서 "성능이 가장 좋아서 선택했다"고 말하지 않는다. 정확한 표현:

> 로지스틱 회귀를 해석 가능한 기준 모델로 두고, 재무변수의 비선형 관계와 상호작용을 학습하기 위해 히스토그램 기반 그래디언트 부스팅을
> 주 모델로 사용했습니다. 구현 환경과 실험 관리의 용이성도 고려했습니다. 다만 여러 알고리즘 가운데 최적이라는 점까지 검증한 것은 아닙니다.

### 5-2. 2차 절차

데이터 시점 문제를 먼저 해결한 뒤(§3·§4), **같은 데이터 · 같은 분할 · 같은 튜닝 예산**에서 후보를 비교하고 **검증 구간 결과로** 고른다.
모델 수를 늘리는 것보다 비교 조건을 공정하게 만드는 것이 우선이다.

1. 로지스틱 회귀 (기준 모델) — 먼저 평가하고 계수 부호를 재무 상식과 대조
2. HistGradientBoosting — 같은 조건
3. 〔확정 필요: 추가 후보와 튜닝 예산 — 예: 후보당 검증 구간 무작위 탐색 N회〕
4. 선택 규칙: 검증 구간 첫 부실 PR-AUC. 차이가 쌍 부트스트랩 구간에서 0 을 포함하면 더 단순한 모델(로지스틱)을 택한다.
5. 설명 카드 · 사이트는 데이터와 평가 기준이 안정된 뒤 2차 모델에 연결한다.

## 6. 평가

- **2024~2025 (T 연도)**: 이미 6번 연 구간이다. 2차에서 다시 돌려도 '처음 보는 평가 자료'가 되지 않는다 → **수정 후 재평가**로만 부른다. 기준을 이 문서로 고정한 뒤 1회 연다.
- **독립 평가**: 개발에 쓰지 않은 자료 = FY2025 사업보고서(T 가 2026년)의 행. 400일 결과 관측이 끝나는 **2027년 5월 이후**에 평가할 수 있다.
  프로그램 종료(2026-12) 전에 **최종 모델과 전처리 기준을 동결하고 해시를 이 문서에 적는다.** 2027년 평가는 그 동결본으로만 한다.

## 7. 설명 카드 웹사이트

카드를 시각적으로 탐색하는 정적 사이트(`site/`). 지금은 **1차 탐색 연구 결과**로 만들고 화면에 그렇게 표시한다.
실명은 쓰지 않는다 (익명 사례 번호 · 사업연도 · 업종 대분류). 2차 결과가 안정되면 같은 화면에 2차 데이터를 연결한다.
