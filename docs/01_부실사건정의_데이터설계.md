# 부실 사건 정의 및 데이터 설계 (v0.1)

**프로젝트**: 국내 상장기업 재무제표 기반 부실예측 모델 구축과 XAI 실무 타당성 검증
**팀**: 종민재 (이종민, 정민재)
**용도**: 1주차 지도교수 1차 면담 논의 자료
**작성일**: 2026-08-28

> 이 문서는 확정본이 아니라 **결정해야 할 것과 그 근거를 정리한 논의용 초안**입니다.
> 면담에서 확정된 내용을 v1.0으로 확정하고, 이후 변경 시 사유와 일자를 기록합니다.

---

## 1. 왜 이 문서가 먼저인가

부실 예측 모델의 성능과 해석은 대부분 **모델링 기법이 아니라 라벨 정의와 시점 처리**에서 결정된다. 특히 다음 세 가지를 초기에 못 박지 않으면 후반부에 결과 전체를 재작업해야 한다.

1. 무엇을 "부실"로 볼 것인가 (사건 정의)
2. 언제 시점의 재무제표로 언제의 사건을 예측하는가 (예측 시계)
3. 정상 기업을 어떻게 고를 것인가 (대조군 구성)

---

## 2. 사건 정의

### 2.1 후보 사건과 성격

| 사건 | 성격 | 공시 확인 경로 | 특징 |
|---|---|---|---|
| 회생절차 개시 신청·결정 | 법적 도산 | DART 주요사항보고서 | 가장 명확한 부실. 표본 매우 적음 |
| 감사의견 거절·부적정·한정 | 회계적 신호 | 감사보고서 | 재무제표와 직결. 표본 상대적으로 많음 |
| 관리종목 지정 | 시장 조치 | KIND 시장조치 공시 | 사유가 다양(재무·비재무 혼재) |
| 상장폐지 | 시장 퇴출 | KIND | 자진상폐·합병 등 부실과 무관한 건 다수 포함 |

### 2.2 권고안 — 2단 구조

**주(主) 정의 (모델 학습용)**
> 감사의견 비적정(거절·부적정·한정) **또는** 회생절차 개시 신청

이유: 둘 다 재무 상태와 인과적으로 연결되고, 발생 시점이 공시로 명확하며, 사유 해석에 모호함이 없다.

**보조 정의 (강건성 검증용)**
> 위 + 재무 사유에 의한 관리종목 지정

이유: 주 정의로 학습한 모델이 보조 정의에서도 유사한 성능을 내는지 확인하면 "라벨 정의에 우연히 맞춘 모델"이 아님을 보일 수 있다. 발표에서 강한 방어 논리가 된다.

### 2.3 제외 규칙 (중요)

다음은 부실로 보지 않는다. 이걸 명시하지 않으면 라벨이 오염된다.

- **자진 상장폐지, 합병·분할로 인한 소멸** — 부실과 무관하거나 오히려 우량한 경우가 있음
- **비재무 사유 관리종목 지정** — 공시 불이행, 사외이사 미달, 지분분산 요건 미달 등
- **스팩(SPAC), 리츠, 투자회사** — 재무제표 구조가 일반 사업회사와 다름
- **금융업(은행·보험·증권·여전)** — 재무비율 체계가 근본적으로 다르므로 별도 처리하거나 제외
- **결산월 변경 직후 기업** — 회계기간이 12개월이 아니어서 비율 왜곡

> **면담 논의점**: 금융업 제외에 동의하시는지. 제외하면 표본이 줄지만 해석이 깨끗해지고, 포함하면 업종 더미를 넣어야 한다.

## 3. 예측 시계 — 이게 가장 위험한 부분

### 3.1 문제

재무제표는 **결산일에 만들어지지 않고 공시일에 이용 가능해진다.** 12월 결산 기업의 사업보고서는 다음 해 3월 말까지 제출된다. 즉 2024사업연도 재무제표를 2025년 1월에 알 수 있다고 가정하면 **미래 정보를 쓴 것**이 된다.

이 실수는 흔하고, 저지르면 성능이 비현실적으로 높게 나온다. 그리고 블라인드 평가에서 실무자가 "이거 실제로는 못 쓰는 정보 아닌가요"라고 지적하면 프로젝트의 신뢰가 무너진다.

### 3.2 권고 규칙

```
기준시점 T = 사업보고서 공시일 (DART 접수일자, rcept_dt)
예측 대상  = T 이후 12개월 이내 사건 발생 여부
사용 변수  = T 시점에 공시로 확인 가능한 정보만
```

즉 재무제표의 **결산일이 아니라 접수일자**를 기준으로 삼는다. DART API가 접수일자를 제공하므로 구현 가능하다.

### 3.3 데이터 분할

시점 기준 분할을 적용한다.

| 구분 | 기간 (제안) | 비고 |
|---|---|---|
| 학습 | 2016 ~ 2022 공시분 | |
| 검증 | 2023 공시분 | 하이퍼파라미터 조정 |
| 평가 | 2024 ~ 2025 공시분 | 최종 성능 보고, 단 1회만 사용 |

무작위 분할(random split)은 **쓰지 않는다.** 같은 기업의 다른 연도가 학습·평가에 나뉘어 들어가면 정보가 새어나간다. 기업 단위 그룹 분할도 함께 적용한다.

## 4. 대조군 구성

두 가지 방식이 있고 트레이드오프가 있다.

**(가) 전수 방식** — 해당 연도 전체 상장사를 정상군으로 사용
- 장점: 실제 운영 환경과 동일한 사건 비율. 성능 지표가 현실적
- 단점: 극심한 불균형 (사건 비율 1~2% 수준 예상)

**(나) 매칭 방식** — 업종·자산규모가 유사한 정상 기업을 사건 기업당 3~5개 매칭
- 장점: 모델이 "업종 효과"가 아닌 "부실 신호"를 학습. 해석이 깨끗함
- 단점: 성능 지표가 실제보다 낙관적으로 보임

**권고**: (나)로 학습하고 (가)로 평가한다. 즉 매칭 데이터로 모델을 만들되, **최종 성능은 전수 데이터에서 보고**한다. 이러면 학습 효율과 보고의 정직함을 모두 얻는다. 보고서에 이 설계를 명시하면 방법론 항목에서 가점 요소가 된다.

## 5. 데이터 소스

| 데이터 | 소스 | 취득 방법 | 비용 |
|---|---|---|---|
| 재무제표 | DART Open API (단일회사 전체 재무제표) | API 키 발급 후 호출 | 무료 |
| 공시 목록·접수일자 | DART Open API (공시검색) | 동일 | 무료 |
| 감사의견 | 감사보고서 본문 또는 XBRL | 파싱 필요 | 무료 |
| 관리종목·상장폐지 | KIND | 조회 후 정리 | 무료 |
| 업종 분류 | KRX 업종코드 | 조회 | 무료 |

**주의 1**: DART Open API는 일일 호출 한도가 있다(계정당 2만 건 수준). 10년 × 2,500사면 단순 계산으로도 한도를 넘기므로, **호출 결과를 로컬에 캐싱**하고 며칠에 나눠 수집하는 구조로 짜야 한다. 이걸 안 하면 3주차에 막힌다.

**주의 2**: 감사의견은 API로 깔끔하게 안 나오는 경우가 있어 감사보고서 본문 파싱이 필요할 수 있다. 여기가 가장 손이 많이 가는 지점이니 3주차에 시간을 넉넉히 두세요.

**주의 3**: API 키는 개인 계정으로 발급받고, **코드에 하드코딩하지 말고** 환경변수나 별도 설정 파일로 분리한다. 결과물을 공개 저장소에 올릴 계획이면 특히 중요하다.

| 범주 | 변수 예시 |
|---|---|
| 수익성 | 영업이익률, 순이익률, ROA, 총자산 대비 EBIT |
| 안정성 | 부채비율, 차입금의존도, 이자보상배율, 유동비율, 자기자본비율 |

| 현금흐름 | 영업현금흐름/매출액, 영업현금흐름/차입금, 순이익 대비 영업현금흐름 비율 |
| 특수 항목 | 자본잠식 여부·정도, 결손금 누적 여부, 계속기업 불확실성 주석 존재 여부, 2년 연속 영업손실 여부 |

## 7. 예상 표본과 위험

계획서 '기타'에 이미 적어둔 대로, 국내 상장사 부실 사건은 표본이 적다. 대략적 예상:

- 연간 상장사 약 2,400사 × 10년 = 관측치 약 20,000건
- 사건 발생: 연 30~60건 수준 → 총 300~500건
- 사건 비율: **1.5~2.5%**

이 수준이면 다음이 발생한다.

| 위험 | 대응 |
|---|---|
| 정확도 지표가 무의미 (전부 정상으로 찍어도 98%) | Accuracy 보고 금지. PR-AUC, 재현율@고정 정밀도로 보고 |
| 성능 지표의 신뢰구간이 넓음 | 부트스트랩 신뢰구간을 함께 제시 |
| SHAP 값이 불안정 | 여러 시드로 반복 후 안정적인 변수만 설명에 사용 |
| 특정 연도에 사건이 몰림 (경기 영향) | 연도별 사건 수를 먼저 그려보고 분할 시점 조정 |

**가장 중요한 것**: 성능이 기대에 못 미쳐도 그것이 실패가 아니다. 계획서에 이미 "한계 자체를 결과의 일부로 기술한다"고 써두었으니, **왜 어려운가를 정량적으로 보여주는 것**이 이 프로젝트의 정직한 성과다. 실무자 인터뷰에서 "이래서 재무제표만으로는 안 된다"는 증언을 받으면 그것이 곧 결론이 된다.

## 8. 지도교수 면담 질문 (5개)

1. 부실 사건을 감사의견 비적정 + 회생절차로 한정하는 것이 타당한지, 관리종목을 주 정의에 넣어야 하는지
2. 금융업을 제외하는 것과 업종 더미로 통제하는 것 중 어느 쪽을 권하시는지
3. 매칭 학습 + 전수 평가 설계에 문제가 없는지
4. 학부 차원에서 접근 가능한 유료 재무 데이터(KIS-Value, FnGuide, TS2000 등)가 있는지 — 있으면 3주차 파싱 부담이 크게 줄어듦
5. 여신심사·신용평가 실무자 섭외에 도움을 주실 수 있는지 (**이게 가장 중요한 질문**)

## A-1. 감사의견 라벨의 동어반복 위험 (심각)

FY2023 사업보고서 안에 FY2023 감사의견이 실려 있다. 그 보고서의 재무제표로 그 의견을
예측하면 예측이 아니라 **동어반복**이다. 성능은 완벽하게 나오고 프로젝트는 무의미해진다.

**결정**: 사건 시점 = 그 의견이 실린 보고서의 접수일자 T_e. 피처는 T < T_e 인 보고서에서만.
`dataset.attach_labels()` 가 `사건일 > 기준시점` 을 강제하며, 이 조건은
`tests/test_smoke.py::test_label_timing` 이 지킨다.

## A-2. 12개월 창이 사건을 통째로 놓치는 문제

FY2021 보고서가 2022-03-25에, FY2022 보고서가 2023-03-28에 접수되면 간격이 368일이다.
계획서대로 창을 365일로 두면 FY2021 행은 **라벨이 0이 된다.** 3일 차이로 사건이 사라진다.
제출 간격은 매년 다르므로 이 손실은 무작위가 아니라 특정 기업에 쏠린다.

**결정 (v0.2)**: 주 분석은 365일을 유지하되 400·450일 민감도를 함께 보고한다.

### 개정 (2026-09-04, 전수 실측) — 주 분석 창을 **400일로 올린다**

전체 3,412사 · 24,965 기업-연도로 실제 측정한 결과, 이건 예외적 사례가 아니라
**일반적인 상황**이었다.

| | |
|---|---|
| 사업보고서 제출간격 중앙값 | **364일** |
| 창 365일 초과 관측치 | 8,401건 (**33.7%**) |
| 창 365일 라벨 | 359건 (1.56%) |
| 창 400일 라벨 | **532건 (2.30%)** — +48% |
| 창 450일 라벨 | 562건 (2.43%) |

제출간격 중앙값이 364일이므로 12개월 창은 **분포의 한가운데를 자른다.**
관측치의 3분의 1이 창을 넘고, 그 행의 사건은 어디에도 붙지 않는다.

그리고 그 손실은 무작위가 아니다.

| 제출기한 연장신고 | 창 초과율 | n |
|---|---|---|
| 없음 | 33.2% | 24,640 |
| **있음** | **79.8%** | 262 |

**2.4배다.** 사라지는 사건은 감사가 제때 끝나지 않은 기업 — 부실 신호가 이미 켜진
기업에 몰려 있다. 12개월 창을 쓰면 가장 중요한 사건부터 지워진다.

**따라서 `HORIZON_DAYS = 400` 으로 올리고, 365·450일을 민감도로 보고한다.**
계획서의 "12개월"에서 벗어나므로 면담에서 확정한다. 근거는 위 두 표다.

## A-3. 시점 분할과 기업 단위 그룹 분할의 충돌

v0.1 §3.3은 시점 분할과 그룹 분할을 모두 적용한다고 썼다. 그런데 둘을 동시에 걸면
'2019년에 학습에 쓰인 기업은 2024년 평가에서 제외'가 되는데, 이는 **실제 운영 환경과 다르다.**
현업에서는 작년에 본 기업을 올해도 심사한다.

**결정**: 시점 분할을 주 설계로 한다. 그룹 분할은 보조 분석으로만 돌려
성능 차이를 보고한다. 같은 기업의 인접 연도 재무제표가 유사해 생기는 낙관 편향은
"인접 연도 중복 제거" 민감도로 별도 확인한다.

## A-6. 공시검색의 `last_reprt_at` — 사건이 사라진다 (2026-09-03 실측)

DART 공시검색(`list.json`)의 `last_reprt_at` 은 "최종보고서만 검색" 여부다.
기본으로 `Y` 를 쓰고 있었는데, 실측해 보니 **원본 공시가 결과에서 빠진다.**

| 2023년 1분기 주요사항보고 | 전체 | 회생절차 |
|---|---|---|
| `last_reprt_at=Y` | 864건 | **5건** |
| `last_reprt_at=N` | 1,526건 | **6건** |

빠진 1건은 디엘팜의 2023-03-16 회생절차개시신청이다. 한 분기에 6건 중 1건(17%)이며,
회생절차는 **주 정의에 속한 사건 유형**이다. 이 비율로 새면 라벨이 무너진다.

같은 문제가 기준시점에도 있다. `Y` 로 사업보고서를 조회하면 정정·첨부추가본만 남으므로,
거기서 최초 접수일을 구하면 **정정본 날짜**가 나온다. 정보가 실제로 공개된 날보다 늦다.
T 가 뒤로 밀리면 예측 창도 함께 밀려 사건이 창 밖으로 나간다 — A-2 와 같은 종류의 손실이다.

**결정**: `dart.disclosures()` 의 기본값을 `N` 으로 바꾼다. 원본·정정본이 모두 오므로
중복은 호출부에서 `min(rcept_dt)` 로 정리한다. 사건 라벨은 '창 안에 하나라도 있는가'라
중복 계상 문제가 없다.

**교훈**: API 기본 파라미터가 무엇을 걸러내는지 확인하지 않으면, 조용히 빠진 데이터를
끝까지 모른다. 성능이 나쁘게 나와도 원인을 찾을 수 없다.
